# 设计取舍

[English](en/design-decisions.md)

这个项目先实现一条能够实际开发、执行、修复和验证的软件工作循环，再通过真实任务识别限制。当前范围是小型本地 Python 项目，后续能力由实验问题驱动。

## 为什么保持单 Agent 与标准库

单个同步循环使模型判断、工具动作和环境反馈的关系容易阅读。标准库 HTTP、文件操作、unittest 和 subprocess 足以支撑这轮体验，减少安装成本，也便于看清 Harness 的实现职责。

Tool 提供动作，Skill 提供方法，MCP 提供外部能力接入；三者都在同一个循环中消费。本轮不引入框架抽象、通用插件发现、Reviewer 或多 Agent 编排。

## 为什么把计划和验证写成门禁

仅在提示词中要求“先计划、最后测试”，不能保证执行过程遵守约定。因此 Harness 在代码中检查工作区查看、计划保存与最终验证。

真实 Job Tracker 运行中，Agent 在 54 项测试通过后再次修改源码，旧验证随即失效，必须重新回归才能交付。另一次接力的代码在外部复验中通过 97 项测试，但 Run 因预算耗尽而未完成最终验证和 `finish`，仍记录为 `TOKEN_BUDGET`。

这两个案例说明：软件当前是否通过测试，与 Agent 是否完成自己的交付合同，需要分别表达。门禁也不能判断测试是否覆盖全部需求，独立验收仍有价值。

## 为什么调整预算与截断恢复

旧输入估算近似把 UTF-8 字节数当 Token，曾预留约 56K，而 API 实际输入约 13K，导致明显提前停止。当前改为 Input / Output 分账，并用 API Usage 动态校准下一次输入预留。

旧长度截断提示要求一次只调用一个工具，后续调用呈现碎片化。当前丢弃截断响应中的工具，提示缩小 edit，并允许多个完整的小调用；单次输出上限从 4,096 提高到 8,192。

这些修改来自真实运行反馈。多项配置同时变化，本轮没有分别隔离各项修改的效果。

## 为什么暂时保留 Full History

完整历史便于观察连续反馈，也避免过早引入摘要状态。但已有仓库需要大量读取，后续每轮请求都会再次携带历史，累计 Input 快速增长。高缓存命中能影响费用，不能减少预算账本中的输入消费。

本轮三次增量运行分别在 250K、800K、400K Input 预算下停止，已经暴露出上下文增长限制。当前没有替代策略的对照结果，因此先保留这个明确基线。

下一阶段优先研究 Context Management，需要同时衡量完成率、连续性、用量、费用、耗时与返工，并进行多任务、多次重复，不能仅凭 Token 下降判断更好。

## 当前边界

| 范围 | 限制 |
|---|---|
| 执行环境 | Linux / WSL2 + Bubblewrap；仅受控 Python 脚本和 unittest，不支持依赖安装、shell 管道或服务编排 |
| 隔离 | 面向可信小项目；没有总磁盘配额、完整系统调用策略或生产多租户保证 |
| 文件工具 | 最多 1,000 文件、单文件 256 KiB，不支持链接、特殊文件和大型仓库索引 |
| 命令资源 | 默认 20 秒；CPU 20 秒、地址空间 512 MiB、单文件 8 MiB，输出超过 1 MiB 终止 |
| 状态延续 | 无 Session 持久化恢复、自动回滚或并发同工作区运行；新 Run 从当前源码重新开始 |
| 模型接口 | 实测配置为 deepseek-v4-flash；当前请求显式发送 thinking，不承诺所有兼容端点可用 |
| 预算与费用 | 输入预留不是精确 tokenizer；缺失 Usage、超额响应和失败请求都影响费用保证 |
| 验证 | 检查命令执行与源码版本，不证明全部需求语义；模型也可能写错测试 |

## 后续方向

1. **Context Management**：控制长任务的历史增长，并验证信息损失与完成率。
2. **Session / Recovery**：保存任务状态，区分对话恢复与仅靠代码现场接力。
3. **Repo Exploration**：减少无差别读文件，提高已有仓库的定位效率。
4. **Reviewer / Subagent**：在明确评审标准后，引入独立检查并验证收益。

对应实验与数据见 [实验结果](evaluation.md)。
